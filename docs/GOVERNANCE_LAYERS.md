# Governance Layers — Inner Loop vs Outer Loop

> One-page map of where governance actually bites in Keel. For the design
> rationale of each layer see the two deep-dives this page links out to:
> [`BUILD_GOVERNANCE.md`](./BUILD_GOVERNANCE.md) and
> [`PERSONA_SKILL_GOVERNANCE.md`](./PERSONA_SKILL_GOVERNANCE.md).

Governance is imposed at **three seams**, not one. Two of them belong to the
**outer loop** (dashboard-initiated work — engine sessions, onboard) and one
belongs to the **inner loop** (developer-initiated work inside the domain
meta-repo). This page ties them together so it's clear what runs where.

## The two loops

```
                              ┌──────────────────────────────┐
                              │  Domain meta-repo (clone)    │
   Developer / CI ─(1)───────▶│  .platform/config/*          │
   `make validate`            │  .platform/scripts/…         │
   `.githooks/pre-commit`     │  .agents/skills/…            │
                              │  repos/**  (submodules)      │
                              └───────────┬──────────────────┘
                                          │
                                          │  same policy files consumed
                                          ▼
                       ┌───────────────────────────────────────┐
   User (dashboard) ─(2)▶ execution.registry.create_session   │
   User (dashboard) ─(3)▶ keel code onboard  (CLI or UI flow) │
                       └───────────────────────────────────────┘
```

- **(1) Inner loop** — you cloned a meta-repo, ran `make init`, and are working
  in an IDE. Governance runs when `make validate` or a git hook invokes the
  profiler. Nothing else consults `skills.yaml` here — the IDE just reads
  whatever `.skills/` files are on disk.
- **(2) + (3) Outer loop** — Keel is orchestrating. Every Build session goes
  through `execution.registry.create_session`; every onboarding goes through
  `keel code onboard`. Both consult the same `governance.yaml` and
  `skills.yaml` the meta-repo carries.

Both loops read from the same policy files, so the dial you turn in one place
shapes both surfaces.

## The three seams

| # | Loop | Seam | Fires when | `off` | `warn` | `enforce` |
|---|------|------|------------|-------|--------|-----------|
| 1 | Inner | `make validate PERSONA=<id>` (repo-side; typical hook: `.githooks/pre-commit` or CI job) | Dev pushes or CI runs | Runs the profile; never fails | Prints denied/out-of-policy skills; still exits 0 | Non-zero exit when a **loaded** skill is `denied` by policy |
| 2 | Outer | `execution.registry.create_session` — the single chokepoint every engine (Devin cloud, Devin CLI, VS Code hand-off) goes through | User launches a Build session | Runs; audit trail tags nothing | Runs; session's audit details carry `governance_level` + `governance_violations` | Refuses launch → `GovernanceViolation` (dashboard surfaces **403**) |
| 3 | Outer | `keel code onboard` (CLI or the dashboard's Onboard flow) | User onboards a repo (with or without a `--domain`) | Installs everything the persona is granted or `default`-permitted | Same as `enforce` filter for skills, plus warning tags in the activity record | Refuses ungoverned onboard (no domain / repo not registered in `repos.yaml`) and installs only persona-permitted skills |

Notes on how the two dials compose:

- **`build_governance`** lives in the domain meta-repo at
  `.platform/config/governance.yaml`. It controls seams **2** and **3**
  (outer loop). Work with no domain follows the platform-wide default set
  from **Admin → Skill governance → Build governance (domain-less default)**
  or `keel admin set-build-governance <off|warn|enforce>`.
- **`skill_enforcement`** is a platform-wide admin toggle (Admin → Skill
  governance, or `keel admin set-enforcement enforce|off`). It only affects
  seam **3** (whether onboard filters skills based on persona policy). Seam
  **1** doesn't need this switch — the persona flag itself decides what the
  profiler reports/gates.
- The two dials are independent on purpose. Build governance can be `enforce`
  (all Build sessions must be domain-scoped) while skill enforcement stays
  `off` (persona policy is advisory) — or any other combination.

## Where the policy lives

```
meta-repo/
├── .platform/
│   ├── config/
│   │   ├── governance.yaml     # build_governance: off | warn | enforce
│   │   ├── skills.yaml         # persona → allow/deny skill globs
│   │   └── repos.yaml          # registered repos (used by onboard's warn/enforce)
│   ├── scripts/
│   │   └── profile_skills.py   # stdlib-only profiler used by `make validate`
│   └── skills-manifest.json    # derived index (regenerated by `make load-skills`)
├── .agents/
│   └── skills/…                # persona + agent skills (baked in)
├── .githooks/
│   └── pre-commit              # canonical inner-loop trigger for `make validate`
└── repos/
    ├── domain-context/…        # tier: domain-validated
    └── <linked>/…              # tier: linked:<name>
```

The profiler classifies every `SKILL.md` by **tier** (`persona`,
`agent-skill`, `domain-validated`, `linked:<repo>`, `local`) — those tiers are
what `skills.yaml`'s `allow`/`deny` globs match against.

## IDE placement, and how governance reaches it

The meta-repo's `Makefile` is **IDE-independent**. `make init` /
`make load-skills` / `make validate` do the same thing on every machine no
matter what IDE is installed:

- Fetch submodules under `repos/**` (`git submodule update`).
- Walk `.agents/skills/`, `.skills/`, `repos/**` for every `SKILL.md`.
- Classify by tier and index into `.platform/skills-manifest.json`.
- With `PERSONA=<id>`, run that index against `skills.yaml` and report /
  fail on denied skills.

None of that touches `.cursor/`, `.codeium/`, or `.devin/`. The profiler
never places files where an IDE reads them — it produces the manifest and
the governance verdict.

**IDE placement is `keel code onboard`'s job.** The onboard step is the
one that is IDE-aware. It picks the target dir by the code-assist tool
(env `KEEL_CODE_ASSIST_TOOL` → detection → `--code-assist-tool` flag →
default `generic`):

| Code assist tool | Repo-local skills dir | Extra step |
|------------------|-----------------------|------------|
| `cursor` | `.cursorrules/` | — |
| `devin` | `.devin/skills/<name>/SKILL.md` | — |
| `windsurf` | `.skills/<name>/` | Bridge into `~/.codeium/windsurf/skills/<domain>__<name>` (symlink by default) |
| `generic` | `.skills/<name>/` | — |

The bridge for Windsurf exists because Cascade doesn't scan repo folders —
only the per-user dir. Symlinks let updates to the repo copy propagate
without a re-install.

Governance reaches the IDE through **two doors** across this placement:

1. **Preventive (physical)** — `keel code onboard` under `enforce`
   (per-domain `build_governance` in `governance.yaml`, or the admin-wide
   `skill_enforcement` toggle) filters skills **before** copying. Denied
   and out-of-policy skills never land in `.cursor/`, `.devin/`, `.skills/`,
   or the Windsurf per-user dir. The IDE "obeys" governance because
   governance trimmed what's on disk for it to load.
2. **Detective (advisory)** — `make validate PERSONA=<id>` reads whatever's
   already on disk against the policy and fails the run (pre-commit hook or
   CI) if a loaded skill is denied. The IDE itself doesn't refuse a
   violating skill — the profiler is what surfaces the drift.

**One-liner takeaway.** If your team's flow is "clone meta-repo + `make init`"
and nothing else, governance is **advisory**: the IDE will happily load
whatever `SKILL.md` files are on disk, and `make validate` just reports.
To make governance **physical** for the IDE, the install has to go through
`keel code onboard` (with `--enforce-skills`, or admin `skill_enforcement`
set to `enforce`) — that's the seam that decides what reaches the IDE-visible
paths.

To close that gap for humans (so a fresh clone doesn't require remembering
the extra command), `make init` now auto-invokes `make ide-install` when
the `keel` CLI is on `PATH`, which runs `keel code onboard --path . --use-domain-skills`
for the meta-repo. If `keel` isn't installed the step prints a hint and
skips — the stdlib-only `make init` guarantee still holds. Set
`SKIP_IDE_INSTALL=1` to opt out (e.g. inside CI containers where IDE
placement is irrelevant).

## Where the skills end up on disk (why you see them twice)

`make load-skills` **indexes** skills into `.platform/skills-manifest.json`.
It does **not** copy anything into an IDE. IDE install happens later, at
`keel code onboard` time, and picks a layout per tool
(`agentic_cli/commands/code.py:_get_skills_dir`):

| Code assist tool | Repo-local skills dir |
|------------------|-----------------------|
| `cursor` | `.cursorrules/` |
| `devin` | `.devin/skills/<name>/SKILL.md` |
| `windsurf` / `generic` | `.skills/<name>/` |

Windsurf/Cascade doesn't scan repo folders, so
`kg/domain_skills.install_skills_to_windsurf()` **bridges** the repo copy into
the per-user directory Cascade actually reads —
`~/.codeium/windsurf/skills/<domain>__<skill>` — using a symlink by default so
updates propagate. That's why the same skill shows up both **in the repo**
(source of truth) and **at the IDE user level** (namespaced pointer): they're
the same folder, published under a domain-scoped name so multiple domains
never collide with each other or with the user's personal skills.

Under `enforce` (seam **3**), the onboard step filters what gets copied at all
— denied and out-of-policy skills never reach the IDE dirs, so the physical
install becomes the access control, not just a report.

## Answers to the specific questions this doc exists for

- **Q: Do we have a document explaining inner + outer loop with the
  context-meta repo?** — this one. Design details are in `BUILD_GOVERNANCE.md`
  (outer loop dial) and `PERSONA_SKILL_GOVERNANCE.md` (persona → skill
  policy).
- **Q: Do we have Makefiles that install skills based on IDE?** — not quite.
  The scaffold's Makefile has `make load-skills`, but it **indexes**
  (`.platform/skills-manifest.json`), it doesn't install. IDE install runs
  from `keel code onboard`, which picks the layout per tool from the table
  above.
- **Q: With inner-loop skills, is governance imposed only in CI/CD?** — no.
  Inner-loop enforcement is repo-invoked, which is *typically* wired through
  a `.githooks/pre-commit` or a CI job running `make validate PERSONA=<id>`,
  but any command that invokes the profiler enforces it — including a
  developer running `make validate` locally. The outer-loop seams
  (`create_session`, `keel code onboard`) also enforce, independently of CI.
  If both loops are set to `off`/`warn`, the IDE will happily use whatever
  skills are on disk — governance only bites the moment a human, CI job, or
  Keel enters one of the three seams.

## Rollout posture

Recommended progression, matching the individual docs:

1. Ship with `build_governance: warn` on every domain and
   `skill_enforcement: off` platform-wide. Nothing breaks; the audit trail
   starts measuring how much ungoverned build activity exists (filter on
   `governance_violations`).
2. Domain teams flip their own `governance.yaml` to `enforce` when ready.
3. Prod posture: admin default `enforce` for both dials — even domain-less
   work is refused, and persona policy filters skills at onboard time.
